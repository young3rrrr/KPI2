# Сувора шарова ізоляція компонентів та відділення обчислювального PricingService від доступу до БД

## Контекст та постановка проблеми
Під час побудови компонентної моделі архітектури системи OpenCRM (Ітерація 1) виникли порушення меж між архітектурними шарами та розбіжності з попередніми моделями Лабораторних 2–4. 
На першій діаграмі контролер DealController напряму звертався до PricingService, сам PricingService мав пряму залежність від DealRepository, а CatalogController викликав ProductRepository в обхід сервісного шару. Крім того, у вхідному шарі API бракувало компонента для перевірки JWT токенів та обмеження частоти запитів (NFR-02, NFR-04).

## Фактори впливу на рішення (Decision Drivers)
* **Наскрізна узгодженість із Лабораторними 3 та 4:** на діаграмах послідовності (SC-01, SC-02) та діаграмі активності координатором угоди є виключно DealService, який сам викликає PricingService та зберігає результати в DealRepository.
* **Чистота шарової архітектури (Layered Architecture):** контролери не повинні звертатися напряму до репозиторіїв БД, а обчислювальні доменні сервіси не повинні змішувати математичні розрахунки із SQL-запитами.
* **Покриття нефункціональних вимог Лабораторної 2:** архітектура повинна явно відображати місце реалізації Rate Limiting (поріг 80 RPS -> HTTP 429) та RBAC/JWT авторизації.

## Розглянуті варіанти
1. **Вільні крос-шарові виклики**, де контролери та обчислювальні сервіси можуть напряму звертатися до будь-яких репозиторіїв.
2. **Мікросервісна декомпозиція** з окремими базами даних для угод, каталогу та сповіщень.
3. **Сувора шарова архітектура (Strict Layered Monolith)** з ізольованим PricingService без доступу до БД, виділеним CatalogService та вхідним Auth & RateLimit Middleware.

## Результат рішення
Обраний варіант: **«Сувора шарова архітектура з ізольованим PricingService та вхідним Middleware безпеки»**. 
Усі HTTP запити проходять через Auth & RateLimit Middleware. Контролери спілкуються лише зі своїми фасадними сервісами (DealController -> IDealService, CatalogController -> ICatalogService). PricingService залишається чистим доменним сервісом без звʼязків із репозиторіями, а всю роботу з БД виконують сервіси володіння сутностями через інтерфейси Data Access Layer.

### Наслідки (Consequences)
* **Добре:** 100% відповідність діаграмам взаємодії Лабораторної 3 (ADR-0003) та бізнес-процесу Лабораторної 4.
* **Добре:** PricingService легко тестувати ізольовано (unit-тестами) без підняття бази даних PostgreSQL.
* **Добре:** централізоване виконання вимог NFR-02 (Rate Limiting) та NFR-04 (JWT/RBAC) на вході в API.
* **Погано:** для простих CRUD операцій каталогу товарів зʼявляється додатковий проміжний шар CatalogService між контролером і репозиторієм.

## Плюси та мінуси варіантів

### Варіант 1: Вільні крос-шарові виклики
* **Добре:** менше проміжних викликів для простих операцій.
* **Погано:** розмиває відповідальність шарів, суперечить Sequence-діаграмам Лабораторної 3 та ускладнює контроль транзакцій.

### Варіант 2: Мікросервісна архітектура
* **Добре:** незалежне масштабування окремих модулів.
* **Погано:** порушує обмеження ресурсів NFR-05 (ліміт 512 МБ RAM на бекенд-контейнер) і створює зайві мережеві затримки для p95 < 200 мс (NFR-03).

### Варіант 3: Сувора шарова архітектура в межах модульного моноліту
* **Добре:** вкладається в ліміт памʼяті 512 МБ RAM та забезпечує низьку затримку викликів між сервісами.
* **Добре:** чіткі контракти provided/required інтерфейсів між усіма шарами системи.
* **Погано:** потребує дисципліни розробки, щоб не допускати прямих імпортів репозиторіїв у контролери.
